## 1. 目的と利用者

静岡県東部（伊豆・駿東地域）で、広告費が見合わず大手ポータルやREINSに載りにくい「持て余し物件」「ワケあり物件」「激安物件」を毎日自動巡回し、新着・消滅の差分を1枚のレポートにまとめるツール。当初の本質は「土地探しでなく再建築可能な"面倒物件"の発見」（`docs/requirements.md` v0.3）。その後、キャンプ場用の山林探し・激安賃貸監視の2用途が加わり、4タブ構成になった。

| タブ（内部id） | 目的 | 適合の目安（§4） |
|---|---|---|
| 更地（`sarachi`） | 市街化調整区域等にある再建築可能な安い土地を、老朽家屋の所有者から安く買い建て替える本命シナリオの土地探し | 種別別上限1,500万円・面積330㎡以上 |
| 家付き土地（`ie`） | 古家付き土地／中古戸建／空き家の**既存建物の再建築可否**を見て安く拾う | 種別別上限3,000万円・面積330㎡以上 |
| キャンプ場土地（`camp`） | ネグラキャンプグラウンド2号店用の広い山物件探し。エリアは **沼津IC起点で車1時間（理想）／1.5時間（網羅）＋価値ある飛び地（下田等）**（2026-09-05 再定義。市町の一覧は §3.5。旧定義「函南町役場から1時間」を包含）。富士山ビューが理想（可視判定はシステム化対象外・目視確認） | 面積1,000㎡以上・価格3,000万円以下（全種別共通・手広く構える方針） |
| 賃貸（`rent`） | 静岡県東部の激安賃貸監視。売買では除外する別荘地も賃貸では狙い目のため除外しない | 月額家賃5万円以下（面積は問わない） |

更地／家付き土地は同じ「home」扱いのサイトから、抽出時の種別判定（shubetsu）で実行時に振り分けられる（サイト単位の固定属性ではない。§5・§6）。

利用者は3名。合言葉キー `ken` / `yumiko` / `ayako` で★・非表示・検索条件を分離する（§7）。
配布URL: `https://neguracg.github.io/akiya-watch/reports/index.html?u=<キー>`

## 2. 用語

| 用語 | 意味 |
|---|---|
| タブ | 更地／家付き土地／キャンプ場土地／賃貸の4区分（上表）。UI上の呼称であり、urls.yamlの`tab:`属性とは1対1ではない |
| 種別（shubetsu） | 更地・古家付き土地・中古戸建・空き家（売買系）／賃貸戸建・賃貸アパート・賃貸マンション・賃貸その他・駐車場（賃貸系） |
| channel | サイトの出自分類（①〜⑧。§3）。tabとは独立の軸（例: キャンプ場土地タブ向けSUUMOはchannel=①・tab=camp） |
| 適合／数値不明／不適合（verdict） | 価格・面積を種別別上限・下限と比較した結果（EARS定義は§4）。表示側の絞り込みに使うだけでサーバ側では除外しない |
| 注意／関心フラグ（caution/interest） | 本文が`caution_keywords`／`interest_keywords`にヒットしたことの印。除外はしない |
| NGエリア | 所在地が`exclude_areas`の地名を含むこと。既定で一覧から隠すが、データからは消さない（除外ログに残す） |
| 検出日（first_seen）／消滅 | 初めて検出された日／一覧から消えて7日以内であること（8日目以降は非表示） |
| バックエンドdedupキー（`key`/`dk`/`bdk`） | `url + "\|" + text[:60]`。1サイト内でのページ跨ぎ重複除去に使い、★・非表示の永続化キーにも使う |
| クロスサイト名寄せキー（`_dk`） | `所在地(正規化)+面積+価格`の完全一致。複数サイトに同一物件が載っているときの画面上のグループ化にのみ使う（保存はされないブラウザ内だけの処理） |
| mode | そのサイトの処理方式。`adapter`(構造化抽出)／`hash`(抽出せず変更検知のみ)／`blocked`(bot対策検出で前回データ保持)／`rebuild`(`--rebuild`実行時) |
| 状態同期 | ★・非表示・検索条件をVPS上のAPIにも保存し複数端末・複数利用者で共有する仕組み（§7） |

## 4. 判定ルール（filters）

`urls.yaml` の `filters:` ブロックが唯一の定義元（`watch.py` にハードコードしない。`CLAUDE.md`）。`camp`・`rent`は基本値（下記「基本」）を上書きマージしたものを使う。

**基本（更地・家付き土地タブ）**

| 項目 | 値 |
|---|---|
| `area_min_sqm`（面積下限） | 330㎡ |
| `price_ceiling_by_type`（種別別価格上限） | 更地/古家付き土地=1,500万円、中古戸建/空き家=3,000万円 |
| `exclude_areas`（NGエリア） | 南箱根ダイヤランド, パサディナタウン, 東大場, エメラルドタウン, 富士見ニュータウン（通学が成立しない別荘地。§11） |
| `exclude_keywords` | 空（建築可否では機械除外しない・恒久方針） |
| `caution_keywords`（13語） | 再建築不可, 要相談, 調査中, 農地転用, 既存不適格, 崖条例, 別荘地, 管理費, 借地, 定期借地, 青地, 農振, 温泉 |
| `interest_keywords`（12語） | 既存宅地, 線引き前宅地, 市街化調整区域, 調整区域, 34条11号, 34条12号, 43条, 再建築可, 建替可, 適合証明, 白地, 無指定 |

**camp上書き**: `area_min_sqm`=1,000㎡、`price_ceiling_by_type`=全種別3,000万円。`exclude_areas`等は基本を継承（別荘地除外がそのまま効く＝キャンプ場用途にも合致するため意図的に維持）。

**rent上書き**（月額家賃・万円）: `area_min_sqm`=0（面積不問）、`price_ceiling_by_type`=全種別5万円、`exclude_areas`=空（別荘地の激安が狙い目のため売買と逆に除外しない）、`caution_keywords`（9語: 事務所, 店舗, 事業用, 駐車場のみ, 高齢者専用, women, 女性限定, 学生限定, 法人契約のみ）、`interest_keywords`（13語: 敷金なし, 敷金無, 礼金なし, 礼金無, ペット可, 駐車場付, 駐車場2台, 庭付, 平屋, 古民家, 戸建, DIY可, 事務所可）。

**適合の定義（EARS）**

- 価格と面積（面積下限が0より大きいタブでは面積も）の両方が取得できているとき、システムはそれらを種別別価格上限・面積下限と比較し、価格が上限以下かつ（面積下限>0の場合のみ）面積が下限以上であれば判定を「適合」とすること。
- 価格が取得できない、または面積下限が0より大きいタブで面積が取得できないとき、システムは判定を「数値不明」とすること。
- 上記いずれにも該当しないとき、システムは判定を「不適合」とすること。
- 所在地または本文が`exclude_areas`の地名を含むとき、システムはその物件をNGエリア該当としてフラグを立てること（一覧からは既定で隠すが、データからは削除しないこと）。
- 本文が`caution_keywords`／`interest_keywords`のいずれかを含むとき、システムはそれぞれ「注意」「関心」のフラグとして保持し、除外には用いないこと。
- 更地/家付き由来のレコードでも面積が1,000㎡以上のとき、システムはキャンプ場土地タブにも表示すること（2026-09-05・§3.5。再クロールせず表示時の`inTabBucket`判定だけで実現。更地/家付き/賃貸タブの判定・表示は変えない）。

## 5. データの流れ

```
urls.yaml(sites)
  → 巡回順を並べ替え（同一ドメイン連続回避＋種別round-robin。LIFULL 202対策）
  → 各サイト: robots.txt確認 → fetch()（1リクエスト総タイムアウト25秒／サイト予算180秒／実行全体55分）
  → 200なら get_adapter(id) で担当アダプタを判定
      - 該当あり → parse_*() でカード抽出＋ページャ追従（アダプタごとに個別ロジック。§9）
      - 該当なし → 抽出は行わずハッシュ監視のみ（2026-09時点で10サイト。§9）
      - BotBlocked例外 → 前回スナップショットを保持し「要確認」扱い（0件で上書きして誤った全消滅にしない）
  → _make_record() で共通スキーマへ正規化（全フィールドは下表）
  → 二層差分: 前回スナップショットのキーと突合し、新規キー=新着(added)、消えたキー=アーカイブへ退避（消滅、7日間だけ一覧に残す）
  → スナップショットへ判定済み値（種別・建築可否・敷金礼金 等）も保存（2026-07-26以降。`--rebuild`が同精度で復元するため）
  → build_html_report() でHTML1枚に全件をJSON埋め込み（サーバ側でのハード除外はしない。絞り込みはブラウザ側）
  → reports/index.html・日付別html/csv・SOURCES.md を書き出し → git commit&push → GitHub Pages公開
```

`_make_record()` が返す正規化レコードの全フィールド:

| フィールド | 意味 |
|---|---|
| `url` | 詳細ページURL（トラッキングパラメータ除去済み） |
| `text` | カードの見出しテキスト（120字まで） |
| `key` | バックエンドdedupキー（§2） |
| `price_man` | 価格（万円。賃貸は月額家賃をfloatで保持、売買はint） |
| `area_sqm` / `area_estimated` | 面積（㎡）／推定値かどうか |
| `tsubo_man` | 坪単価（万円/坪。賃貸は常にNone） |
| `shubetsu` / `shubetsu_reason` | 種別／判定根拠 |
| `ceiling_man` | このレコードに適用された種別別価格上限 |
| `chimoku` | 地目（宅地/畑/山林等。取れなければ「—」） |
| `toshikeikaku` | 都市計画区分（市街化調整区域/市街化区域/「—」） |
| `setsudo` | 接道の生テキスト（幅員○m 等。取れなければNone） |
| `rebuild_mark` / `rebuild_reason` | 建築可否○△×/不明とその理由（賃貸は常に「—」・対象外） |
| `zokujinsei` | 属人性（農家住宅/分家住宅）の疑い（bool） |
| `verdict` | 適合／不適合／数値不明（§4） |
| `interest` / `caution` / `ng_areas` | ヒットしたキーワード／NGエリア名のリスト |
| `location` / `machi` | 所在地（生）／判定された対象市町 |
| `madori` / `chikunen` / `kanrihi` / `shikikin` / `reikin` | 間取り/築年/管理費/敷金/礼金（賃貸アダプタのみ設定） |
| `first_seen` / `last_seen` | 初検出日／最終確認日 |

## 7. 状態同期（?u=キー）

**構成**: 本体はGitHub Pages（静的）のまま。★・非表示・検索条件だけをVPS（`https://staff.negura.website/akiya-state`、`state-api/`）のAPIにも保存するハイブリッド構成。2026-07-26に本番投入（メモリ記載。以降の稼働状況の再確認は本書の範囲外）。

**localStorageキー**（すべて`akiyawatch_`接頭辞）: `tab` / `price` / `area` / `hidden` / `fav` / `exareas` / `ukey`。除外エリアには旧キー`akiya.exareas.v2`からの自動移行がある。

**APIエンドポイント**: `GET /healthz`（認証不要・DB疎通確認）、`GET`・`PUT /state/{key}`（`key`は`ken`/`yumiko`/`ayako`のいずれか、allowlist外・未登録キーは常に404）。認証機構はなく、キー文字列自体が合言葉（`state-api/README.md`）。`?u=`の形式は`^[a-z0-9_-]{1,32}$`、`?u=off`で記憶を消して同期を明示解除できる。

**「どちらが勝つか」の規則**: pull（GET）は**キー単位でマージ**する——サーバに値がありこの端末でまだ変更していないキーはサーバ優先で上書き、この端末で変更済み（dirty）のキーはローカルを維持する。サーバが完全に空（未登録相当）なら、初回シードとしてローカルの値をそのままpushする。PUTは操作から800msデバウンスし、ページ離脱時は`keepalive`付きfetchで送信を試みる（`sendBeacon`はPUTを送れないため不使用）。

**キー切替時の挙動**: 前回このブラウザで使ったキーと異なるキーに切り替えた場合（または初めての利用）、ローカルの状態（tab/price/area/hidden/fav/exareas）を全消去し、サーバ側の値だけを採用する。前の利用者の★等が新しいキーへ誤って引き継がれる事故を防ぐための仕様（実例が過去にあったため導入。`docs/BUGLOG.md`）。

## 9. アダプタの型

**契約**: `parse_*(first_html, base_url, filter_keywords, filters, session) -> list[dict]`。1ページ目のHTMLは呼び出し側（`run()`）が取得済みのものを渡す。ページャ追従・待機（2〜8秒のランダムスリープ）・サイト固有のbot対策検出は各アダプタ内で行い、`_make_record()`由来の正規化レコードのリストを返す。取得を諦める場合は`BotBlocked`例外を送出する（`run()`側が前回スナップショットを保持し「要確認」に倒す）。

**新サイト追加の手順**: ①`urls.yaml`へのURL追加（`CLAUDE.md`の実測(a)(b)＋承認手順を経てから）②専用`parse_*`関数の実装、または既存関数の再利用（`id`の前方一致で流用可能。例: `parse_suumo`はキャンプ場土地タブのSUUMO8サイトにも流用されている）③`SITE_ADAPTERS`への登録——**前方一致の順序が重要**で、特殊化した接頭辞（例: `suumo_rent_`）は元の接頭辞（`suumo_`）より必ず前に置く（後ろだと食われて誤ったパーサが呼ばれる）④`SOURCES.md`は次回実行で自動反映される。

## 10. 制約・非機能

**外部ライブラリ方針**: `watch.py`の依存は`requests`／`beautifulsoup4`／`pyyaml`の3つのみ（`requirements.txt`）。ブラウザ自動化ライブラリは導入していない。そのためJS描画・持続的なbot対策のサイトは実装せず、`sources_extra`へ「フェーズ2」等として記録するに留める（§11）。`pytest`（`tests/`。§12参照）はテスト実行時のみの開発依存で、この3つの実行時依存には含めない（`requirements.txt`は変更していない）。

**bot対策で落ちるサイトの扱い**: アダプタが`BotBlocked`を検出した場合、そのサイトは今回の抽出をスキップし前回スナップショットをそのまま保持したうえで「要確認」フラグを立てる。0件で上書きして誤って「全消滅」と判定することを防ぐ（`run()`参照）。

**public repoである前提**: リポジトリ・GitHub Pagesとも公開（`noindex`付き）。個人情報を入れない前提（`state-api`も★/非表示/検索条件のみを保存し機微データは置かない設計。`state-api/README.md`）。

**安全装置**: 1リクエストの総タイムアウト25秒（`FETCH_TOTAL_TIMEOUT`。requestsのtimeoutは細切れ送信に効かないため、使い捨てデーモンスレッド＋joinで強制打ち切り）、1サイトあたり180秒（`SITE_TIME_BUDGET`）、実行全体55分（`RUN_WALLCLOCK_LIMIT`＝3300秒。超過時は残サイトを打ち切ってレポートを出す。2026-09-05に30分から引き上げ＝§8）。

**1回のクロール所要時間**: 保証されるのは上限55分のみ。サイト間に2〜20秒のスリープを挟むため、サイト数（2026-09-05時点で140。同日中に118→140への追加が2バッチに分かれて行われた）の増加とともに実測時間も増える傾向にあり、旧上限30分では直近5回中3回で実際に上限到達・末尾サイトの打ち切りが発生していた（`gh run view --log`実測。§8・`docs/BUGLOG.md`）。**140サイト化後の実測（`gh run view --log`）は本バッチ完了時点で未実施**——次回Actions実行後に55分上限へどの程度の余裕があるか確認すること（残リスク）。
